No production secret is generated by this implementation. Generate at least

into chat, shell history, source, logs, or PRs. Never configure production voice

The endpoint hashes both candidate and configured bearer authorization before
constant-time comparison. No request bodies, auth headers, user IDs, owner IDs,
RPC errors, or ledger data are logged. Responses are no-store and contain only
sanitized result classes and the incoming request ID on success.

Lambda only emits `{request_id, request_timestamp}`. The endpoint rejects every
extra field, malformed JSON, oversized bodies, non-JSON content, and non-POST
methods. It verifies the configured owner through Auth admin lookup, checks
`ledger_capabilities` using the existing shared contract validator, and invokes
ONLY `alexa_log_water`. Missing config, unavailable owner, or missing
`alexa_water_v1` capability fails closed before mutation.

## Database bridge and migration

Migration: `20260929000100_alexa_water_bridge.sql`.

`public.alexa_log_water(p_owner uuid, p_event uuid, p_operation uuid,
p_completed_at timestamptz)` is SECURITY DEFINER with empty fixed search_path,
qualified objects, no dynamic SQL, and EXECUTE granted only to `service_role`
(apart from the function owner/DB administrators). EXECUTE is explicitly revoked
from PUBLIC, anon, authenticated. No existing table RLS policy is changed.

The bridge revalidates the owner and ledger, UUIDv5 IDs, distinct event/operation
IDs, and finite millisecond completion time. It builds exactly one
`water_events.put` containing `gallons=1`, `legacy=false`, with an empty remove
list. There is no arbitrary payload or caller-selected table/action input.

To reuse the unchanged owner-aware `ledger_read`/`ledger_apply` primitives, the
function scopes `request.jwt.claim.sub` to the resolved owner **inside the DB
transaction only**, restoring its previous value on success or exception. This
is an internal execution context, not a stored/minted/refreshed/emulated Auth
login session: no JWT, refresh token, Auth session, or personal login credential
is created or consumed. Authorization comes from the bridge's explicit SQL
grant, never from a caller-provided claim. No privileged raw event INSERT is used.

The existing owner advisory lock is held before loading the current revision
and calling `ledger_apply`. A short SHARE ROW EXCLUSIVE lock on `water_events`
also serializes event-ID collision checks against inserts from any owner; this
prevents the privileged underlying upsert from overwriting an existing event.
This can briefly serialize Waterdrop writes across owners, acceptable for this
private integration. An operation-ID advisory lock serializes cross-owner
operation identity checks. Existing PWA revision conflict behavior is unchanged.
The endpoint retries SQLSTATE 40001 at most once, with identical arguments and
the same total HTTP deadline; normal appends resolve their revision inside the
bridge transaction and do not require a long-lived client revision.

Event and existing durable `ledger_operations` receipt commit atomically through
`ledger_apply`. Replays must match the existing event semantics AND receipt hash.
Incompatible identities fail, and a replay never recreates an event later deleted
by the user. An identity collision is rejected, not converted into an update.
No existing rows, financial calculations, backup schema, or browser code change.

`ledger_capabilities` adds `alexa_water_v1`, retaining contract version 2 and all
existing capabilities. Authenticated clients can still discover capabilities;
service_role gains capability discovery without a user login. Anonymous access
remains denied. The PWA does not require this optional voice feature; the server
does. Normal migration preflight nevertheless BLOCKS deployment until migration
history matches. Do not bypass that check.

## Identity, time, replay and limits

Protocol v1 uses UUIDv5 (SHA-1 per RFC UUIDv5, tested against a known vector), name
`alexa:` followed by the validated Alexa requestId, with permanent namespaces:

- Event: `e7ae804e-e367-51c8-a4ac-d3939c982071`
- Operation: `57b5e84c-d718-5a36-830d-273daac218a0`

These are public protocol constants, not credentials. Never replace them on a
retry or ordinary release. Same request ID produces same IDs; changed timestamps
with the same identity are rejected. Completion time is the original Alexa UTC
request timestamp, normalized to millisecond ISO format; never receipt/retry time.
New operations must be within five minutes past / one minute future of DB time.
Exact committed replays can be older (endpoint sanity floor 2020); the DB checks
the receipt and event before expiry/rate admission. SQL audit timestamps remain
server-managed. Request trust depends on the restricted ASK trigger plus required
skill/account checks and the private Lambda→server secret.

For unique voice operations, a durable per-owner budget allows fewer than 30
existing receipts in the last minute and fewer than 200 in the last day. This
counts **all** owner ledger receipts, including PWA activity; heavy normal use may
therefore temporarily block a new voice command. It never limits PWA writes.
Owner serialization makes concurrent admission safe. Existing exact replays
bypass the budget and do not consume it again. No in-memory/server-instance quota
is relied upon, and deleting a water event does not erase its operation receipt.

Lambda's HTTP deadline is six seconds, with redirects disabled and no automatic
transport retry. The server's shared upstream deadline is 4.8 seconds. A timeout
may follow a commit; replaying the **same request** recognizes its receipt and
returns success without a second gallon. A fresh spoken command is a NEW request
and can legitimately add another gallon. Failure speech is always honest:
“I couldn't confirm the gallon with 50-A.” Never infer nothing was saved.
Success/replay speech: “Added one gallon to 50-A.”
